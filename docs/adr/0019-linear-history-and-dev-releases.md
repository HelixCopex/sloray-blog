# ADR-0019：线性历史与 dev 驱动的人工批准发布

* 状态：已接受
* 日期：2026-10-09

## 约束

项目维护者要求日常开发提交到 `dev`，主分支只保存获准发布的版本。
版本递增与发布时机由维护者决定，不能由 CI 或编码代理自行决定。
全部分支需要线性历史；主分支发布提交必须与开发分支通过 CI 的提交一致。
现有 CI 的 push 触发范围没有包含 `dev`，无法提供这一发布前提的验证证据。

## 决策

使用 `dev` 集成开发，`main` 作为发布分支。所有分支禁止 merge commit，
共享的 `dev` / `main` 禁止重写历史；临时分支在集成前整理成可快进的提交链。
CI 增加 `dev` 的 push 触发和真实源分支的线性历史检查。

维护者先批准发布与目标版本号，版本变更仍提交到 `dev`。包含版本变更的
最新提交必须重新通过完整 push CI，并记录获准 SHA、版本号与 CI run。
每个版本将 `main` 一次以 `--ff-only` 推进至该 SHA，随后建立对应版本标签。
发布后继续在 `dev` 开发；紧急修复遵循相同流程。

不使用 squash/rebase merge 发布，因为它们会改变已验证提交的 SHA；
不使用 merge commit，因为它会破坏线性历史。

## 后果

贡献者和编码代理必须在 `dev` 提交后续更改，CI 成功不构成发布授权。
快进失败、开发分支新增提交或 CI 未全部成功时，发布必须重新协调与确认。
仓库文档和 CI 保存工作流约定；远程访问控制仍需维护者配置 GitHub 规则，
不把本地 Git 配置或文档声明误当作已生效的托管平台保护。

具体操作与验证要求见 [贡献指南](../../CONTRIBUTING.md)。
