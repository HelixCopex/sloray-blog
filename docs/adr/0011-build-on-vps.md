# ADR-0011：在 VPS 上编译部署，而不是在 CI 构建二进制

**状态**：已接受

## 背景

部署有两种做法：

1. **CI 构建 + 分发二进制**：GitHub Actions 编译好 `sloray-api`，
   打包成 tarball，通过 SSH 传到服务器安装。
2. **在目标机器上编译**：服务器上 `git pull` + `cargo build --release`，
   前端也本地 `pnpm build`，然后原子切换。

最初选的是方案 1。后来改为方案 2。

## 决策

采用方案 2。CI 只做**质量门**（`fmt` / `clippy` / `test` / 迁移冒烟 / `astro check`），
不再产出与分发二进制。

## 理由

1. **glibc 兼容问题直接消失。** 这是方案 1 最隐蔽的坑：二进制链接的 glibc
   版本就是运行环境的**最低**要求。Debian 12 是 2.36，如果 CI 跑在
   ubuntu-24.04（2.39）上构建，二进制在 Debian 12 上会直接
   `GLIBC_2.39 not found`。方案 2 链接的就是本机 libc，这个问题不存在，
   也就省掉了"构建机版本必须钉死"这类隐性约束。
2. **少一条供应链。** 不需要 artifact 存储、部署 SSH 私钥、
   `DEPLOY_*` secrets、跨机版本对齐。
3. **增量编译让日常发布很快。** `target/` 跨发布复用：实测冷编译 203 秒，
   而只改一处应用代码后的增量重编译只要 **32 秒**。方案 1 每次都是全量链接。
4. **单机部署场景下，"构建环境与运行环境一致"比"构建一次多处部署"更有价值。**
   后者是为多台服务器准备的，而这里只有一台。

## 代价（实测，见 docs/deployment.md）

| 项 | 实测值 |
|---|---|
| 冷编译峰值内存（`-j1`） | **1.06 GB** |
| 冷编译峰值内存（`-j2`） | **1.35 GB** |
| 冷编译时间（`-j1` / `-j2`） | 203 s / 109 s |
| 依赖下载 | 376 MB |
| `target/` | 556 MB |
| 前端 `node_modules` + store | 228 MB |

**最关键的一条：2 GB 内存的机器上不能用 `-j2`。**
1.35 GB 的编译峰值加上 Postgres / Caddy / Node 的常驻内存就会 OOM。
因此 `deploy-on-vps.sh` 的 `CARGO_JOBS` 默认为 **1**，并要求配 swap 兜底。

副作用（其实是好事）：`-j1` 只占一个核，发布期间另一个核还能服务请求。

## 重新评估的触发条件

1. 发布频率高到"在服务器上编译"成为痛点；
2. 需要**一次构建、多台部署**（例如加了第二台 VPS 或做了蓝绿双机）——
   那时方案 1 的收益才会真正出现，且必须配套钉死构建镜像；
3. 服务器规格小到连 `-j1` 都 OOM（那就只能回到方案 1，或上 musl 静态构建）。
