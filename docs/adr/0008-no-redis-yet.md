# ADR-0008：暂不引入 Redis，并写明触发条件

**状态**：已接受

## 背景

「分布式博客」的默认技术清单里通常有 Redis：缓存、会话、计数、限流、
队列都往上放。但每多一个常驻进程，就多一份内存占用、监控、备份、
升级与故障面 —— 在单台 VPS 上这个成本是实打实的。

## 决策

**M0–M5 不引入 Redis。** 各项需求先用已有手段满足：

| 需求 | 现方案 | 为什么够用 |
|---|---|---|
| 页面缓存 | HTTP 缓存（`Cache-Control` + CDN/Caddy） | 读流量倾斜，HTTP 层缓存命中率最高，且不需要应用参与 |
| 会话 | Postgres `sessions` 表（ADR-0007） | 数据库已经在，且天然多实例共享 |
| 限流 | 进程内 `tower_governor` | 单机单实例下等价于全局限流 |
| 浏览计数 | `post_view_daily` 唯一约束去重 + `post_stats` 原子自增 | 用唯一约束换正确性，无行锁竞争路径 |
| 异步任务 | Postgres `outbox` + `FOR UPDATE SKIP LOCKED` | SKIP LOCKED 让单机队列天然支持多消费者 |

## 理由

* 上面每一项都已经能在**不引入新故障源**的前提下正确工作。
* `SKIP LOCKED` 与唯一约束是"用数据库的正确性保证替代中间件"，
  在单机规模下总复杂度更低，而且**将来多节点时行为不变**。
* 提前引入 Redis 会掩盖真正的瓶颈所在。

## 影响与触发条件

达到以下任一条件时，重新评估本决策（新写一条 ADR 取代它）：

1. **出现第二个 API 节点**：进程内限流不再等价于全局限流。
2. **计数写入成为瓶颈**：`post_stats` 的热点行自增开始明显排队，
   此时改用 Redis `INCR` + 定期回写，并**接受**进程重启丢失在途计数的语义
   （必须写进文档，而不是让运维猜）。
3. **需要跨请求的短期状态**：例如验证码、一次性 token、防重放窗口。
4. **缓存命中率证明 HTTP 层不够**：出现大量无法用 URL 作为键的重复计算。

引入时注意：Redis 在本架构里**只能是缓存/派生**，
不能成为任何数据的唯一存放处（ADR-0005）。
