# ADR-0001：只保留两个可部署单元，不拆微服务

**状态**：已接受

## 背景

需求里出现了「分布式」这个词。在工程实践里，这个词很容易被翻译成
「多拆几个服务、加个消息队列、上个 K8s」，但对一个博客来说，
这些手段解决的是它并不存在的问题。

## 决策

整条业务链路上只有两个可部署进程：

* `sloray-api` —— Rust（axum + SeaORM），唯一数据权威；
* `sloray-web` —— Astro SSR，负责呈现与局部导航。

将来可能出现第三个：`sloray-worker`（outbox 投递、派生图、定时发布）。
它是**在真正需要异步处理时**才出现的，而不是一开始就预留。

## 理由

1. **拆分不产生可用性。** 单机上一台 VPS 挂了，拆成 5 个进程也一样挂。
   真正的可用性来自：无状态进程 + 外部化状态 + 备份/PITR + 只读副本。
2. **拆分的代价是立刻支付的**：跨进程调试、分布式追踪、契约版本管理、
   部署协调、超时与重试语义。而收益（独立伸缩）在博客的负载下几乎为零 ——
   读多写少、写入量以「天」为单位。
3. **业务边界不清晰时拆分会固化错误的边界。** 现在还没有足够的领域知识
   去判断「评论」和「计数」该不该在同一个服务里。

## 影响

* 需要水平扩展时，把 `sloray-api` 多起几个实例放在 Caddy 后面即可
  （`deploy/systemd/sloray@.service.in` 已经是模板单元）。
* 「分布式就绪」通过**进程无状态 + 外部化状态**实现，见
  `docs/architecture.md` 的第 4 节清单，而不是通过服务拆分。

## 重新评估的触发条件

* 某条路径的负载特征与其余部分截然不同（例如搜索压垮了正文读路径）；
* 某个组件的伸缩单位与进程不同（例如需要 GPU 的图片处理）；
* 团队规模增长到需要独立发布节奏。
